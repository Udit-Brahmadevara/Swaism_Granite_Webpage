# Swasim Granite — website

Static marketing site for Swasim Granite (Hosur, Tamil Nadu): quarry owners,
processors and exporters of Indian granite.

Plain HTML, CSS and ES modules — no framework, no runtime dependencies. The
publish directory is **`public/`**; everything outside it is tooling and source
material and is never deployed.

## Quick start

```bash
npm run serve      # http://127.0.0.1:4173 — behaves like Cloudflare (see "Local server")
npm run check      # static self-check; run after any edit
npm run verify     # smoke test against the running server
```

Needs Node 18+. The image, map and share-card builders also need Python 3 with
Pillow (and fontTools for the share card).

## Layout

```

  *.html                  GENERATED by tools/pages.py — do not edit by hand
  _headers                caching + security headers (Cloudflare Pages / Netlify)
  sw.js                   service worker (cache name stamped by tools/bump-sw.mjs)
  robots.txt sitemap.xml  GENERATED by tools/pages.py
  favicon.ico  apple-touch-icon.png
  assets/
    css/site.css          one stylesheet, sectioned; tokens at the top
    js/data.js            ALL site content: stones, markets, articles
    js/core/              pure helpers: dom, carousel, service-worker registration
    js/components/        chrome (header, footer, NAV), cards, lightbox, world map
    js/pages/             one thin controller per page
    fonts/ brand/ img/ granite/ monuments/
tools/
  pages.py                SOURCE of every page's markup, the sitemap and robots.txt
  serve.mjs               local server that mirrors the production host
  check.mjs               static self-check (see "Checks")
  verify.mjs              smoke test against a running server or the live site
  bump-sw.mjs             stamps the service-worker cache name
  build-images.py         re-encodes photographs from source-assets/
  build-share-card.py     builds public/assets/img/share-card.jpg
  bake-map.py             pre-renders the world map SVG
  build-holding.py        builds holding/index.html

```

## The rules worth knowing

1. **Page markup lives in `tools/pages.py`, not in `public/*.html`.** The HTML
   files are regenerated in full by `npm run pages`, so an edit made directly to
   one is silently lost the next time anyone runs it. Each file says so in its
   `<head>`.
2. **Content lives in `public/assets/js/data.js`.** Stones, markets,
   articles and contact details are defined once and rendered by the page
   controllers.
3. **Style lives in `public/assets/css/site.css`, driven by the `:root` tokens.**
   No `style="…"` anywhere, in markup or in JS templates: the CSP blocks inline
   styles, so a colour set that way silently disappears in production.
4. **Every internal URL is root-absolute and extensionless**: `/about`,
   `/catalogue#tan-brown`, `/assets/css/site.css`. Never `about.html`, never
   `assets/…`.
   - *Extensionless* because Cloudflare redirects `/about.html` → `/about`. That
     costs a round trip on every click, and a service worker that caches the
     redirected response makes the browser reject later navigations outright —
     which broke every link for returning visitors before it was fixed.
   - *Root-absolute* because the host serves `404.html` at whatever URL was
     missing. From `/catalogue/granite/x`, a relative `assets/…` path resolves to
     `/catalogue/granite/assets/…` and the 404 page renders unstyled.

`npm run check` enforces rules 3 and 4.

### Layering

Dependencies point one way only: `pages → components → core → data`. Nothing in
`core/` imports a component, and nothing imports a page.
`components/chrome.js` is the one module with a side effect — importing it
mounts the header and footer — which is why every page controller ends with
`import '../components/chrome.js'`.

## Rebuilding

```bash
npm run pages      # regenerate HTML, sitemap and robots; restamp the worker; check
npm run images     # re-encode photographs from source-assets/
npm run map        # re-bake the world map (needs /tmp/countries-110m.json)
npm run share      # rebuild the social share card
npm run build      # all of the above
npm run bump       # restamp the service worker after a hand edit to CSS or JS
```

The service worker caches pages, CSS, JS, photographs and fonts, and a new cache
name is the only thing that makes an installed worker let go of them.
`tools/bump-sw.mjs` hashes what it caches — code by content, photographs by name
and size — into that name. `npm run check` fails if the stamp is stale, so a
hand edit to the CSS cannot ship without it.

## Checks

`npm run check` inspects `public/` and fails on:

- a class used in markup or a template that no CSS rule defines
- an internal path that does not resolve
- a relative URL, or a link to `*.html`
- an inline `style="…"` in markup or a JS template
- a page `<head>` drifting out of sync with the others
- a third-party subresource or an `<iframe>`
- robots, sitemap, 404 or favicon out of step with the pages, or a `.html` canonical
- a photograph missing its WebP twin or grid-size copy, or an image named in
  `data.js` that does not exist
- a stale service-worker cache stamp
- a CSP that allows inline script

`npm run verify` fetches what a browser would from the running server: every
page at its real URL, a deep 404 that still loads its styles, the metadata, the
spam trap and the security headers. Against the live site it also checks that
`http://` redirects to `https://`:

```bash
node tools/verify.mjs --url https://www.swasimgranite.com
```

## Local server

`npm run serve` runs `tools/serve.mjs` rather than a plain file server, because
three production bugs were invisible under `python3 -m http.server`. It:

- applies `public/_headers`, so a CSP violation shows up locally first
- redirects `/page.html` → `/page` and serves `/page` from `page.html`, exactly
  as Cloudflare does
- answers every missing path, however deep, with `404.html` and a 404 status

`node tools/serve.mjs 8080 --no-pretty` behaves like a plain host instead.

## Deploying (Cloudflare Workers)

The site deploys as a Cloudflare Worker with static assets: no Worker script,
just the files in `public/`. Everything about the deployment lives in
`wrangler.jsonc`, so it is version-controlled rather than dashboard state.

| Environment | Worker (dashboard name) | Domain | Deploys on a push to |
|---|---|---|---|
| Staging — client review | `swasim-granite-preview` | `preview.swasimgranite.com` | `main` |
| Production | `swaism-granite-webpage` | `www.swasimgranite.com` + `swasimgranite.com` | `production` |

Both Workers build from this repo with Workers Builds (**Worker → Settings →
Build**): build command empty, deploy command `npm run deploy:staging` or
`npm run deploy:production`, non-production branch builds off. Both commands
run `npm run check` first and stop if it fails. Cloudflare deploys to the
connected Worker whatever `name` the config gives. The top level of
`wrangler.jsonc` is staging, so a bare `wrangler deploy` from a laptop can never
reach the live domain.

**Domains.** Staging's custom domain comes from `wrangler.jsonc`. Production's
two domains are attached in the dashboard on `swaism-granite-webpage` (the route
`www.swasimgranite.com/*` and the custom domain `swasimgranite.com`), and the
production environment deliberately sets `"routes": []`. Wrangler only publishes
routes when the list is non-empty, and when it does it replaces every route on
the Worker. The empty list must stay explicit: without it, production inherits
the top-level route and a deploy would pull `preview.swasimgranite.com` onto the
live Worker. A redirect rule sends the bare domain to `www`, where the canonical
URLs point.

Staging differs from production in three deliberate ways:

- it is meant to sit behind **Cloudflare Access** (a Zero Trust self-hosted
  application on `preview.swasimgranite.com` that admits only listed emails).
  Not set up yet: Zero Trust needs a card on the account, even on the free plan
- `_headers` marks it `noindex`
- it never installs the service worker, so after each deploy the client sees
  the new build on an ordinary refresh

### Publishing a change

1. Open a PR and merge it into `main`. The preview site updates about a minute later.
2. The client checks it on `preview.swasimgranite.com`.
3. Put it live: `git switch main && git pull && git push origin main:production`.

### Launch (one-time)

1. Client sign-off on the preview; `npm run check` and `npm run verify` pass.
2. Dashboard: **SSL/TLS → Edge Certificates → Always Use HTTPS: on**, and
   **Analytics & Logs → Web Analytics → Manage site → Disable** (the CSP blocks
   its injected script, and the privacy policy promises no analytics).
3. `git push origin main:production` to create the release branch.
4. `swaism-granite-webpage` → **Settings → Build** → connect this repository:
   production branch `production`, build command empty, deploy command
   `npm run deploy:production`, non-production branch builds off. Its build
   replaces the holding page on both domains, with no gap.
5. Dashboard: **Rules → Redirect Rules**, wildcard pattern: request URL
   `https://swasimgranite.com/*`, target `https://www.swasimgranite.com/${1}`,
   301, preserve query string on.
6. `node tools/verify.mjs --url https://www.swasimgranite.com`.

To roll back, open `swaism-granite-webpage` → **Deployments** and roll back to an
earlier version. The holding page is one of them.

`_headers` is also read by Netlify. On nginx or similar: gzip or brotli on;
`public, max-age=31536000, immutable` for `/assets/fonts/`; one day for the other
`/assets/` image folders (their files are regenerated in place, so they must
not be `immutable`); `no-cache` for `/sw.js`; and `try_files $uri $uri.html =404`
with `error_page 404 /404.html`.

## Performance

Built for buyers on slow, high-latency connections. Measured in Chromium on a
throttled phone connection — 390px wide, 1.6 Mbps, 300 ms round trips, first
visit, no cache:

| | Before | After |
|---|---|---|
| Home: largest contentful paint (hero photo) | 3.8 s | **1.9 s** |
| Home: layout shift (CLS) | 0.891 | **0** |
| Catalogue: layout shift (CLS) | 0.263 | **0.002** |
| Third-party origins | 0 | 0 |

What does the work:

- **No third-party requests.** Every byte comes from this origin: self-hosted
  fonts, a pre-rendered map, no embeds, no analytics. On a 300 ms link each
  extra origin costs a DNS lookup and a TLS handshake before its first byte.
- **Preload hints.** `tools/pages.py` walks each page's module imports and emits
  `<link rel="modulepreload">` for the whole graph, plus a preload for the first
  hero photograph (read from `HERO` in `data.js`). Without them the browser
  discovered modules three levels deep, one round trip at a time, and could not
  request the hero photo until all of them had run.
- **Reserved space** for everything JavaScript renders (the end of `site.css`),
  including the phone hero carousel and the catalogue detail panel — the two
  sources of the shifts above. Update the values if that content changes size.
- **Two sizes, two formats per photograph** (`tools/build-images.py`), so a grid
  tile never downloads a full slab, and WebP is used where supported.
- **Fonts self-hosted**, latin subset, only the weights in use; the two used
  above the fold are preloaded.
- **The world map is pre-rendered** (`tools/bake-map.py`): a 50 KB SVG instead of
  d3, TopoJSON and an atlas. The bake also cuts rings at the antimeridian and
  drops overseas territories far from their mainland, so highlighting "Europe"
  does not put a patch in South America.
- **The hero loads one slide,** the rest when the browser is idle.
- **A service worker** serves photographs and fonts cache-first and pages, CSS
  and JS stale-while-revalidate, so a repeat visit is near-instant and works
  offline. It never stores a redirected response.

## Colour

Every page's masthead (the striped band at the top) takes one of the logo's four
colours, and the four repeat in menu order:

| Page | Masthead | Class | Text |
|---|---|---|---|
| `/` | green, the hero (`--brand-gradient`) | `.hero` | cream, gold accents |
| `/about` | gold, from the G | base `.masthead` | ink, green accents |
| `/catalogue` | blue | `.masthead--blue` | cream |
| `/what-we-do` | red | `.masthead--red` | cream |
| `/contact` | green | `.masthead--green` | cream, gold accents |
| `/privacy` | gold | base `.masthead` | ink, green accents |
| `/404` | blue | `.masthead--blue` | cream |
| `/articles`, `/brochure`, `/testimonials` (hidden) | red, green, gold | | |

To change a page's colour, change the modifier on its `<section class="masthead">`
in `tools/pages.py` and run `npm run pages`.

The colours are sampled from the logo: green `#134932`, gold `#E09D08` (the G,
kept as `--logo-orange`), blue `#1B4AA8` and red `#C61E1D` (the bars). The bands
(`--brand-gradient-band`, `--band-green`, `--band-blue`, `--band-red`) sit close
to those, a shade deeper where the copy needs it. Each ground dictates its text:

- **Gold** `#CC9008` to `#DDA416`: ink copy, 6.2:1 at the darkest stop, with deep
  green accents (4.6:1). Cream fails here (2.6:1), so copy runs dark.
- **Blue** `#163E92` to `#2253B4`: cream copy at 94% (6.1:1 or better). Gold
  would measure 2.9 to 4.0:1, so accents are cream.
- **Red** `#A8191A` to `#BD2220`: cream at 94% (5.2:1 or better). Gold drops to
  2.5:1, so accents are cream.
- **Green** `#0A3A22` to `#0F4C2E`: cream at 94% (8.6:1 or better), gold accents
  (5.2:1 at the deep end, where the eyebrow sits).

Masthead copy is solid or near-solid, never faint: at 72% cream, the blue and
red bands miss the 4.5:1 body threshold. Small labels use `--muted` (`#6f6a5e`,
5.1:1 on the paper background). The keyboard focus ring is `--focus`: deep green
on light grounds and the gold masthead, gold on green, cream on blue and red, at
least 3:1 everywhere.

## Mobile

The phone layout follows the **"Swasim Mobile"** artboard (10 screens at
402×874), which is a distinct design rather than a narrowed desktop. One
codebase serves both; the phone-specific decisions live in the *Mobile
treatment* section of `site.css`, plus a little progressive behaviour in the
page controllers.

| Artboard decision | Implementation |
|---|---|
| Hero is a full-bleed photo with copy overlaid at the bottom | `.hero__text` is *repositioned* over the carousel, not duplicated |
| Tightened hero sentence on phones | `.lede--mobile`, swapped by media query |
| Founding stats sit below the photo, not over it | `.hero__stats` |
| "Featured lots" scroll sideways | `.marquee`: every stone in one continuously sliding row, at every width |
| Catalogue search | `.search` + `[data-search]`; filters compose with the type chips |
| Catalogue browses two-up | `.thumb-grid` / `.gallery` at two columns |
| Tap a stone → its detail | detail scrolls back into view (`scroll-margin-top` clears the sticky header) |
| Tap-to-call and WhatsApp | `.contact-actions` → `tel:` and `wa.me` |
| 48px minimum touch targets | applied to every control under 900px |
| Hamburger with a short gold third bar | `.nav-toggle__bars` |

**Deliberately not copied:** the artboard's `‹ … ⋯` iOS navigation bars. Those
are app chrome, meaningless on a web page with real browser navigation.

**One divergence worth a decision:** the artboard's phone hero headline reads
"Stone from our own quarry benches.", where desktop reads "Excellence Carved in
Stone". Serving a different `<h1>` per viewport would give the page two
competing headlines and hurt search indexing, so the desktop headline is used at
every width and only the supporting sentence switches.

## Common edits

| Task | Where |
|---|---|
| Change page copy or structure | `tools/pages.py`, then `npm run pages` |
| Change a stone's facts or photo | `public/assets/js/data.js` → `GRANITES` (`facts` holds origin, found in, applications and properties). To replace a photo, overwrite its master in `source-assets/granite/` and run `npm run images`: every page uses the one file, and the headers and service worker make browsers pick it up on the next load. A stone with `img: null` is held back until its photo exists |
| Change the home carousel | `data.js` → `HERO`: a photo slide is `{ img, name, kicker, alt }` (photo into `source-assets/hero/`, then `npm run images`); a catalogue stone is `{ stone: 'viscount-white' }`. Run `npm run pages` if the first slide changes |
| Add a stone | Master into `source-assets/granite/`, a line in `GRANITE_NAMES` in `tools/build-images.py`, `npm run images`, then append to `GRANITES` |
| Give a stone multiple photos | Add `images: [{ src, alt }, …]` to it — arrows, dots and swipe appear automatically |
| Add monument photos | Masters into `source-assets/monuments/`, `npm run images`, bump the count in `MONUMENTS` |
| Publish testimonials | `data.js` → `TESTIMONIALS`; an entry renders only without `sample: true` |
| Change phone, email or address | `data.js` → `COMPANY`, the footer address in `chrome.js`, and in `tools/pages.py` the contact-page locator (place, region, directions link) and description, the JSON-LD and the privacy text |
| Re-theme colours or spacing | `site.css` → `:root` tokens |
| Change a repeated card's markup | `public/assets/js/components/cards.js` |
| Add a nav item | `public/assets/js/components/chrome.js` → `NAV` (`/page`, no `.html`) |
| Hide or publish a page | `HIDDEN` in `tools/pages.py` (noindex, out of the sitemap) and `hidden: true` on its `NAV` entry in `chrome.js`, then `npm run pages`. Articles, Brochure and Testimonials are hidden for now |
| Add a page | A `PAGES[...]` entry in `tools/pages.py`, a controller in `js/pages/`, a `NAV` entry, `npm run pages` |
| Change the product list | `data.js` → `PRODUCTS` (`wide: true` spans the row) — and the "Five ways" heading in `tools/pages.py` |
| Change the About page equipment list | `data.js` → `CAPABILITIES` (Infrastructure & Capabilities section). To give a machine a photo: master into `source-assets/infrastructure/`, `npm run images`, then add `img: '/assets/infrastructure/<name>.jpg'` and `alt` to its entry, plus `credit: { by, license, href }` if the photo is openly licensed rather than the client's own |
| Add or change the footer icon links | `data.js` → `SOCIAL` (an entry without an `href` shows its icon but is not clickable), and keep the profile URLs in step with `sameAs` in the JSON-LD in `tools/pages.py` |
| Change the affiliations | `data.js` → `AFFILIATIONS` (text tiles; confirm each `role` with the client) |
| Add or replace a facility photo | Master into `source-assets/facility/`, `npm run images`, then list it in `FACILITY` in `data.js` (caption and alt required; the first entry shows first) |
| Connect the contact form | `FORM_ENDPOINT` in `js/pages/contact.js`, **and** its origin in `connect-src` in `_headers` |

## Launch checklist

Done, and verified by `npm run check` / `npm run verify` where it can be:

| Item | Where |
|---|---|
| Privacy policy | `/privacy`, linked from every footer |
| Custom 404 that works at any depth | `404.html`, root-absolute paths, `noindex`, not in the sitemap |
| Sitemap + robots.txt | generated by `tools/pages.py` |
| Canonical URLs | every page, extensionless, from `SITE_URL` |
| Social preview | `assets/img/share-card.jpg`, 1200×630 |
| OpenGraph + Twitter cards | every page |
| Structured data | `Organization` JSON-LD on the homepage and contact |
| Security headers | HSTS, CSP (no inline script or style), nosniff, `X-Frame-Options` in `_headers` |
| Spam protection | honeypot + 3s time trap in `js/pages/contact.js` |
| No cookies, no analytics, no third-party requests | checked in-browser: 0 of each |
| Accessibility basics | label contrast 5.1:1, focus ring ≥ 3:1, skip link, reduced-motion support |
| Favicon | `favicon.ico` (16/32/48) + `apple-touch-icon.png` |

**Still open:**

1. **Cloudflare:** Always Use HTTPS, and the apex → `www` redirect (see "Deploying").
2. **Contact form delivery.** The form validates and then opens WhatsApp (app
   or WhatsApp Web) with the enquiry pre-filled, and the buyer presses send.
   A buyer without WhatsApp only gets the note pointing them to the email
   address. For delivery that asks nothing of the buyer, set `FORM_ENDPOINT`
   and add its origin to `connect-src`, then rewrite the privacy policy's
   "How it reaches us" paragraph to name the provider.
3. **Masthead colours**: settled, one logo colour per page (see "Colour").
4. **Client sign-off on factual claims:** the affiliation roles in
   `AFFILIATIONS` (CAPEXIL member, DGFT-registered exporter, STONA participant)
   and the use of each body's logo, the "since" year for each export market (the
   Middle East has none yet, and its countries — UAE, Saudi Arabia, Qatar, Oman,
   Kuwait — are an assumption), Emerald Green's origin, the plant equipment described in
   `PROCESS`, the hero's lot and quarry numbers, and the plant address on
   the contact page (it shows no map coordinates until the client supplies the plant's pin). The Emerald Green and Kuppam Green photos are other
   suppliers' watermarked images: replace them with the client's own slab photos.
5. **Testimonials** — the six entries in `TESTIMONIALS` are invented design copy
   and carry `sample: true`, so none of them render; the page shows an honest
   "we're gathering these" state. Add real, approved quotes without the flag.
6. **Articles** — the listing shows titles and excerpts only; there are no
   article pages yet, so the cards are deliberately not links.
7. **Brochure PDF** — `/brochure` describes the contents and routes to the
   contact form. Link the PDF when it exists.
8. **Photography** — every granite master is 1000×1000, and the two quarry
   photographs in the home carousel (`source-assets/hero/`) are only 540 and 700px
   wide, so they look soft on a full-width phone hero. The quarry photographs in
   particular do not look like the client's quarry. Confirm every photo shows the
   client's own stone, plant or quarry and is licensed, and replace with larger
   originals.
9. **Hero carousel pause control** — it pauses on hover and focus and respects
   reduced motion, but WCAG 2.2.2 asks for a visible pause button on content that
   rotates for more than five seconds.
10. **Privacy policy review** — written against the real data flows, but not
    legal advice. Fill in the retention period and the named hosting and email
    providers once chosen.

**No cookie banner is needed as the site stands**, and adding one would be
theatre: there is nothing to consent to. That stops being true the moment anyone
adds Google Analytics, an embedded map or video, or a chat widget. If analytics
are wanted, a cookieless one (Plausible, Umami, Cloudflare Web Analytics) keeps
it that way; GA4 does not.
